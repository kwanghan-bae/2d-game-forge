# 신의 마을: 영원의 후원자 — 한글 Production Game Design Specification

> **문서 상태:** V4 구현 기준선 (soft-launch 후보 검증 전)
> **작성일:** 2026-09-06
> **최종 정합성 점검:** 2026-09-07
> **대상 프로젝트:** `games/inflation-rpg`
> **대상 플랫폼:** 모바일 우선(iOS / Android), 웹 개발 셸 병행
> **참고작:** Evil Hunter Tycoon
> **문서 목적:** 현재 프로젝트의 분산된 V3 방향을 하나의 출시 가능한 제품 정의와 실행 기준으로 통합한다.

---

## 0. 이 문서가 결정하는 것

이 문서는 기존 프로젝트의 모든 시스템을 출시 범위로 인정하지 않는다. 현재 저장소에는 단발성 인플레이션 RPG에서 `Eternal Hero` 방치형 후원 시뮬레이션으로 이동하는 과정에서 생성된 시스템, 데이터, 문서가 함께 존재한다. 이 문서는 그중 출시 제품에 필요한 공통 방향을 기준선으로 지정한다.

이 문서가 최종적으로 결정하는 제품은 다음과 같다.

> 플레이어는 조선 설화 세계의 신이 되어 하나의 영원한 영웅과 작은 마을을 후원한다. 영웅은 스스로 살아가고 싸우며, 플레이어는 마을의 시설·지원 에이전트·후원 정책을 조정해 영웅의 생존과 성장, 그리고 사가의 방향을 바꾼다.

출시 1차는 다음을 제공한다.

- 영원한 영웅 1명
- 지원 에이전트 3명
- 핵심 마을 시설 7개
- 대표 Realm 3개
- 자동 전투·원정·제한적 오프라인 진행
- 영웅의 나이·노화·회춘·사가 기록
- 레벨·장비·시설 강화·후원 정책 성장
- 선택형 광고와 단순한 IAP

현재 구현 계약:

- 기본 `StartGame()`은 `신의 마을: 영원의 후원자` V4를 마운트하고, V3는 `StartLegacyGame()`과 `inflation-rpg-legacy`로 보존한다.
- V4 저장 키는 `shin-ui-eternal-sponsor-v4-save-v1`이며 schema 1을 사용한다. V3 저장 키와 자동 migration·덮어쓰기를 공유하지 않는다.
- V3 영웅 가져오기는 영웅 상세 화면의 명시적 동작으로만 실행한다.
- 오프라인 진행은 최대 8시간, 온라인 효율 70%이며 위험 Realm의 보스 결과와 다음 Realm 해금은 자동 확정하지 않는다.
- 출시 V4에는 별도의 가족·가계·지원 에이전트 생애/사망 시뮬레이션을 넣지 않는다.

다음 항목은 출시 1차의 전제조건이 아니다.

- 16명 이상의 플레이어블 영웅
- 20개 던전과 600개 named floor
- PvP, 길드, 실시간 협동
- 자유 배치형 마을 건설
- 영웅 모집 가챠
- 모든 기존 시스템의 UI 노출
- 무제한 신규 재화 추가

## 1. 현재 프로젝트 분석

### 1.1 프로젝트 구조

현재 저장소는 `pnpm workspace + Turborepo` 기반의 2D 게임 monorepo다. 공통 코어와 게임별 workspace를 분리하고, 개발 환경에서는 `apps/dev-shell`, 출시 환경에서는 게임별 Next.js export와 Capacitor를 사용한다.

현재 게임 workspace의 주요 기술은 다음과 같다.

| 영역 | 현재 기술 | 기획서 영향 |
|---|---|---|
| UI | React 19 | 마을·메뉴·요약 화면 구현에 적합하다. |
| 월드·전투 | Phaser 3.90 | 자동 이동, 전투 장면, 시각적 이벤트에 사용한다. |
| 상태 | Zustand | 영웅·마을·세이브 상태의 단일 진원지로 유지한다. |
| 저장 | Zustand persist + migration | 오프라인 보상과 버전 전환을 위해 migration을 계속 유지한다. |
| 배포 | Next static export + Capacitor 8 | 서버 의존 없는 single-player 출시를 우선한다. |
| 테스트 | Vitest + Playwright | 순수 계산·스토어·모바일 핵심 흐름을 모두 검증한다. |
| 수익화 | AdMob + 원스토어 IAP 계약 | 선택형 광고와 비강제 IAP 정책으로 재정의한다. |

게임 코드는 V4 `TownHub → Hero/Expedition/Saga` 구조를 기본으로 사용하고, 기존 `CyclePrep → Overworld → CycleResult` 흐름은 legacy 진입점에서만 유지한다. V4의 순수 영웅 결정·전투 계산은 adapter 경계로 재사용하며 V3 store mutation과 cycle 종료는 공유하지 않는다.

### 1.2 현재 상태의 핵심 문제

1. 제품 정체성이 문서마다 다르다.
   - 초기 문서는 단발성 BP 기반 인플레이션 RPG를 설명한다.
   - `Content 300h` 문서는 20개 던전과 7층 메타 케이크를 확장한다.
   - V3 문서는 한 영웅을 무기한 후원하는 방치형 시뮬레이션으로 전환한다.

2. 기능 표면이 출시 범위를 초과한다.
   - 여러 종류의 화폐, 유물, Ascension, Realm, 신격 보구, Paradox Spiral, 시즌, 도전과제, NPC 생애가 동시에 존재한다.

3. 핵심 선택의 우선순위가 흐리다.
   - 플레이어가 매 세션 무엇을 확인하고 어떤 결정을 내려야 하는지 한 문장으로 정의되어 있지 않다.

4. UI·문서·기술 상태가 다르다.
   - 기존 V3 심층 시스템과 V4 출시 화면이 같은 workspace에 공존한다.
   - V4는 이를 기본/legacy manifest와 전용 저장 키로 분리하고, 제한적 오프라인 보상으로 재방문 루프를 만든다.

### 1.3 작업 트리 보호 기준

문서 작성 시점에 다음 파일은 작업 중 변경 상태로 확인되었다.

- `games/inflation-rpg/src/systems/paradoxSpiral.ts`
- `games/inflation-rpg/src/systems/paradoxSpiral.test.ts`
- `games/inflation-rpg/src/systems/paradoxSpiralBalance.test.ts`

이 문서는 위 변경을 되돌리거나 수정하지 않는다. Paradox Spiral 관련 구현은 출시 1차에서 비노출 대상으로 분류하며, 별도 확장 계획에서 다시 다룬다.

## 2. Evil Hunter Tycoon 역설계

### 2.1 참고작의 핵심 구조

Evil Hunter Tycoon은 플레이어를 Town Chief로 두고, Town Hall을 중심으로 Trading Post, Bounty Hut, 생산 시설, 상점, Academy, Enhancement Forge, 버프 시설을 연결한다. 공식 건물 문서상 마을은 재료를 모으고, 상품을 생산하고, 헌터가 그것을 구매하고, 헌터의 성장과 원정을 지원하는 운영망으로 설계되어 있다.

헌터는 직업·등급·특성·HP·허기·기분·기력과 같은 상태를 가지고, 플레이어는 헌터를 직접 선택해 장비 구매, 훈련, 치료, 원정, 활동을 지시할 수 있다. 던전은 최대 5명의 헌터가 입장하고 마을이 원정 비용을 부담하며, 결과 아이템은 마을의 소유가 된다. 환생은 레벨 100에서 레벨을 초기화하고 영구 능력과 특성 포인트를 제공하는 장기 성장 장치다.

### 2.2 참고하는 요소와 버리는 요소

| 참고 요소 | 우리 게임에 적용 | 적용하지 않는 부분 |
|---|---|---|
| Town Chief 역할 | 플레이어를 `신`이자 마을 후원자로 정의한다. | Town Chief의 모든 직접 명령을 복제하지 않는다. |
| 시설 간 생산·소비 연결 | 치료·제작·훈련·원정이 서로 자원을 소비하도록 만든다. | 출시 초기에 복잡한 다단계 생산 체인을 넣지 않는다. |
| 자율 헌터 | 지원 에이전트가 작업 큐를 자율 수행한다. | 다중 헌터 수집과 대규모 roster는 후속으로 미룬다. |
| 던전 원정 | 원정소에서 영웅의 목적지와 위험도를 설정한다. | 20개 던전·600층을 초기 요구사항으로 삼지 않는다. |
| 특성·욕구 | 영웅 성격과 에이전트 특성에 반영한다. | 배고픔·기분·기력·치료를 모두 독립 게이지로 만들지 않는다. |
| 환생 | 회춘으로 한 영웅의 시간을 되돌린다. | 영웅을 소모하고 새 영웅으로 교체하지 않는다. |
| PvP·길드·대규모 운영 | 확장 백로그로만 보관한다. | 출시 1차 범위에 넣지 않는다. |

### 2.3 참고작에서 얻는 제품 교훈

1. 자동 진행 게임에도 플레이어의 관리 역할을 한 문장으로 설명해야 한다.
2. 마을 시설은 장식물이 아니라 캐릭터의 행동과 자원 흐름을 바꿔야 한다.
3. 에이전트의 특성은 단순 수치가 아니라 행동 선택에 영향을 줘야 한다.
4. 실패는 손실만 주지 말고 다음 시도의 준비 방향을 보여줘야 한다.
5. 장기 성장에는 레벨 상승과 다른 종류의 리셋·회춘 장치가 필요하다.
6. 마을·던전·성장·수익화를 한 번에 확장하면 late-game 난이도와 결제 피로가 커질 수 있으므로 출시 범위를 먼저 제한해야 한다.

## 3. 제품 정의

### 3.1 제품 한 줄

**한 영웅의 삶을 마을과 후원으로 바꾸어 가는 조선 설화형 idle management RPG다.**

### 3.2 플레이어 역할

플레이어는 다음 세 가지 역할을 동시에 수행한다.

- 신: 영웅의 행동 방향과 후원 정책을 결정한다.
- 마을 운영자: 시설과 지원 에이전트의 병목을 해결한다.
- 기록자: 영웅의 생애와 지원 에이전트 신뢰도, 실패, 업적을 사가로 보존한다.

### 3.3 제품의 차별점

일반적인 idle RPG는 숫자 상승과 보상 수령을 중심으로 한다. 이 게임은 다음 차이를 갖는다.

1. 영웅은 수집 가능한 카드가 아니라 시간이 누적되는 하나의 인격이다.
2. 마을의 강화가 영웅의 수치뿐 아니라 행동 선택과 생존 패턴을 바꾼다.
3. 노화와 회춘이 장기 운영의 긴장감을 만든다.
4. 플레이어의 선택이 사가 기록과 지원 에이전트 신뢰도 변화로 남는다.
5. 조선 설화의 신·무당·도깨비·저승·산신을 시스템 언어로 사용한다.

### 3.4 디자인 기둥

| 기둥 | 검증 질문 |
|---|---|
| 살아있는 영웅 | 영웅이 플레이어가 없어도 자기 성격에 따라 행동하는가? |
| 작지만 작동하는 마을 | 시설을 바꾸면 영웅의 다음 행동이 체감되게 달라지는가? |
| 짧은 개입, 긴 결과 | 1~3분의 조작이 10분 이상 진행에 영향을 주는가? |
| 기록되는 인생 | 전투·신뢰도·실패가 나중에 다시 읽을 수 있는 기록으로 남는가? |
| 설화 기반의 해석 | 서양 판타지 이름만 바꾼 것이 아니라 시스템 의미가 한국적 언어로 설명되는가? |

## 4. 핵심 플레이 루프

```text
[자동 생활]
영웅 이동 · 전투 · 회복 · 사건 · 에이전트 작업
        ↓
[상태 확인]
HP · 나이 · 장비 · 신뢰도 · 생산 큐 · 다음 위험
        ↓
[신의 개입]
정책 변경 · 시설 지시 · 장비 교체 · 개입 사용
        ↓
[원정 또는 생활 결과]
재료 · 금화 · 신력 · 균열석 · 기록 · 해금
        ↓
[다음 자동 생활]
```

### 4.1 세션 길이

| 세션 | 목표 경험 |
|---|---|
| 30초 이하 | 보상 수령, 영웅 상태 확인, 정책 유지 |
| 1~3분 | 시설 작업 지시, 장비 교체, 신의 개입 1회 |
| 5~10분 | 원정 준비·사건 선택·장비 강화·스토리 확인 |
| 하루 1회 | 나이 변화, 에이전트 신뢰도, 업적, 기록관 확인 |

### 4.2 핵심 행동 정책

기존 `SponsorDirective`를 제품의 핵심 플레이어 입력으로 승격한다.

| 정책 | 영웅 행동 | 보상·위험 |
|---|---|---|
| 공격 | 보스·위험 지역·전투를 우선한다. | 희귀 보상 증가, 부상 위험 증가 |
| 비축 | 안전 지역·귀환·재료 확보를 우선한다. | 안정적인 수입, 성장 속도 감소 |
| 수련 | 훈련·안전한 사냥터·시설 이용을 우선한다. | 레벨·경험치 성장 증가, 희귀 보상 감소 |

정책은 영웅의 현재 상태를 직접 덮어쓰지 않고 행동 가중치를 변경한다. V4 출시판의 최종 판단은 정책·HP·나이·현재 Realm을 사용하며, 별도 영웅 성격 축은 후속 콘텐츠로 분리한다.

### 4.3 신의 개입

신의 개입은 플레이어가 자동 흐름에 직접 개입하는 제한 수단이다.

- 출시 종류: 즉시 회복, 후퇴 명령
- 충전: 기본 1회 지급, 보상형 광고로 1회 추가
- 저장 상한: 3회
- 후퇴 시 원정 준비 비용의 50%를 돌려주며 장비·영구 재화는 잃지 않는다.
- 전투 강제 승리·보상 증폭·사건 재판정 개입은 출시 범위에 넣지 않는다.
- 기록: 개입은 사가에 남긴다.

## 5. 마을 설계

### 5.1 마을 화면 원칙

출시 1차 마을은 자유 배치형 시뮬레이션이 아니라 고정형 hub다.

- 화면 하나에서 영웅, 3명의 에이전트, 7개 시설, 현재 생산 큐를 확인한다.
- 시설마다 작업 중·대기·시작 불가 상태를 한눈에 표시한다.
- 중요한 상태는 아이콘만 사용하지 않고 텍스트와 수치로 함께 표시한다.
- 시설을 열기 위해 여러 화면을 순차 탐색하지 않는다.
- 마을 진입 후 3초 안에 “지금 가장 먼저 처리할 병목”을 파악할 수 있어야 한다.

### 5.2 출시 시설 7개

| 시설 | 역할 | 레벨 업 효과 | 시작 상태 |
|---|---|---|---|
| 신전 | 신력 생산·후원 기반 | 생산량·작업 시간 | Lv1 노출 |
| 회복당 | 영웅 HP 회복 | 회복 작업 효율 | Lv1 노출 |
| 대장간 | 장비 제작·강화 | 생산량·작업 시간 | Lv1 노출 |
| 훈련소 | 영웅 경험치·행동 성장 | 경험치·작업 시간 | Lv1 노출 |
| 무당집 | 균열석 생산·원정 보정 | 생산량·보정 효율 | Lv1 노출 |
| 원정소 | Realm 선택·원정 파견 | 원정 시간 | Lv1 노출 |
| 기록관 | 사가 정리·장기 기록 | 생산량·작업 시간 | Lv1 노출 |

### 5.3 시설 작업 큐

각 시설은 작업 큐를 가진다.

```ts
interface FacilityTask {
  id: string;
  facilityId: string;
  type: string;
  startedAt: number;
  completesAt: number;
  input: Record<string, number>;
  outputPreview: Record<string, number>;
  assignedAgentId: string | null;
}
```

규칙:

- 시설당 활성 작업은 기본 1개다.
- 출시 1차는 시설별 활성 작업 1개만 허용한다. 추가 슬롯은 후속 범위다.
- 작업을 취소하면 재료의 80%만 반환한다.
- 작업 결과는 완료 시 확정한다.
- 앱 종료 중에도 시간 기반 작업은 진행한다.
- 선택형 사건이 필요한 작업은 오프라인 중 자동 확정하지 않는다.

## 6. 지원 에이전트

### 6.1 출시 에이전트

| 에이전트 | 핵심 능력 | 주요 실패 모양 |
|---|---|---|
| 대장장이 | 제작·강화·재련 | 재료 부족, 처리 지연 |
| 무당 | 정화·축복·원정 보조 | 축복 효율 저하, 사건 지연 |
| 길잡이 | 위험도 예측·원정 보조 | 보상 예측 오차, 위험 증가 |

### 6.2 공통 상태

```ts
interface SupportAgent {
  id: 'blacksmith' | 'mudang' | 'guide';
  nameKR: string;
  roleKR: string;
  level: number;       // 1~3
  trust: number;       // 0~100
  fatigue: number;     // 0~100
  trait: string;
  activeTaskId: string | null;
}
```

에이전트는 플레이어블 영웅과 같은 생애 시뮬레이션을 갖지 않는다. 출시 1차의 에이전트는 작업 큐, 특성, 피로도, 신뢰도만 가진다. 이는 다중 NPC 생애와 마을 생산 시뮬레이션을 동시에 구현하는 위험을 제한한다.

### 6.3 신뢰도와 피로도

- 신뢰도는 장기적으로 유지되는 지원 자원이다.
- 피로도는 작업이 끝날 때 증가하고 휴식 작업으로 감소한다.
- 피로도가 80 이상이면 작업 속도가 15% 감소한다.
- 피로도가 100이면 새 작업을 받지 않는다.
- 신뢰도 50 이상이면 해당 에이전트를 전문 작업에 배정할 때 전문 보정이 적용된다.
- 신뢰도 100은 장식 보상과 사가 이벤트를 해금한다.

## 7. 영웅 설계

### 7.1 영웅 생애

| 나이 | 챕터 | 시스템 의미 |
|---|---|---|
| 5~14 | 성장기 | 튜토리얼·첫 전투·첫 사건 |
| 15~29 | 청년기 | 장비·첫 Realm |
| 30~49 | 전성기 | 최대 성장 효율·주요 원정 |
| 50~69 | 노화 시작 | 회복·이동·공격 효율 감소 |
| 70+ | 쇠약기 | 회춘 판단·희귀 사건 |

영웅은 V4에서 영구 사망하지 않는다. 원정 패배는 영구 장비·재화 손실 없는 중단으로 처리하고 회복을 유도한다. 노화와 자원 압력으로 장기 운영의 선택을 만들며, 별도 생애 종료 상태는 출시 범위가 아니다.

### 7.2 회춘

출시 UI는 5년 회춘을 제공하며, domain adapter는 양의 정수 기간을 지원한다. 최소 나이는 5세다.

```text
회춘 비용
= 되돌린 연수 × 10 금화
```

회춘 시 유지하는 것:

- 레벨
- 장비
- 시설·Realm 해금
- 사가 기록

회춘 시 변경하는 것:

- 현재 나이
- 나이 기반 능력 배율
- 행동 시계와 해당 나이 표현
- 회춘 카운터

### 7.3 영웅 성격 (후속 확장)

영웅 성격 축은 장기 차별화 후보로 보존한다. V4 출시판에는 별도 성격 배열을 저장하지 않고 후원 정책 3종으로 행동 가중치를 제공한다.

후속 성격 축 후보:

- 용맹: 보스·위험 지역 선호
- 신중: 회복·귀환·안전 지역 선호
- 호기심: 미지 사건·유적·희귀 경로 선호
- 신앙: 무당집·신전·축복 효과 선호
- 탐욕: 보상 증가, 위험 감수

후속 도입 시 목적지 선택·후퇴 판단·사건 선택 중 최소 2개에 연결되어야 유효한 특성으로 인정한다.

## 8. 원정·Realm·전투

### 8.1 출시 Realm

| Realm | 테마 | 해금 | 핵심 자원 |
|---|---|---|---|
| 조선 평야 | 시작 마을·산길·들판 | 시작 | 금화·기초 재료 |
| 깊은 숲 | 도깨비·짐승·폐사찰 | 조선 평야 보스 승리 후 명시적 확인 | 고급 재료·균열석 |
| 저승 | 혼령·강·재판 | 깊은 숲 보스 승리 후 명시적 확인 | 균열석·고급 재료 |

기존 `sea`, `volcano`, `heaven`, `chaos` 등은 후속 Realm으로 보존한다.

### 8.2 원정 흐름

```text
원정소 진입
  → 목적지 선택
  → 위험도·예상 보상 확인
  → 정책·장비·에이전트 확인
  → 출발
  → 자동 이동·전투·사건
  → 귀환 또는 중단
  → 보상·사가·신뢰도 반영
```

출시 1차에서는 동시에 1개의 원정만 진행한다. 원정 슬롯 확장은 신전 레벨 후속 콘텐츠로 남긴다.

### 8.3 전투 등급

| 등급 | 목표 전투 시간 | 첫 도전 기대 승률 | 실패 결과 |
|---|---:|---:|---|
| 일반 | 8~15초 | 90~97% | HP 감소, 마을 귀환 |
| 정예 | 20~40초 | 65~80% | 부상, 일부 보상 |
| 지역 보스 | 45~90초 | 45~65% | 원정 중단, 재도전 정보 |

### 8.4 전투 수식 기준

```text
영웅 전투력
= 공격력 + 방어력 + floor(최대 HP / 100)

예상 승률
= 등급별 기본값(일반 92% / 정예 72% / 보스 55%)
  + 권장 전투력 대비 준비도 보정
  + 길잡이 신뢰도·정책·무당집 보정
  - Realm 위험도·낮은 HP 보정
  → 5%~97%로 제한

실제 전투는 V3 순수 타격·피해 경감 계산을 V4 runtime adapter에서 결정론적으로 호출한다. 동일 저장 상태와 원정 ID는 동일한 판정을 재현해야 한다.
```

각 항은 데이터 테이블로 분리한다. 화면 컴포넌트나 Phaser 씬에서 난이도 수치를 직접 계산하지 않는다.

### 8.5 실패 UX

실패 결과는 반드시 다음을 보여준다.

- 부족했던 능력치
- 적의 주요 위험 요인
- 추천 시설
- 추천 장비 또는 정책
- 재도전까지 예상 소요 시간
- 회춘 또는 지원 에이전트 강화의 기대 효과

실패로 장비를 파괴하거나 영구 재화를 잃지 않는다.

## 9. 성장·재화 설계

### 9.1 출시 성장축

| 축 | 역할 | 출시 여부 |
|---|---|---|
| 영웅 레벨 | 기본 전투력 | 출시 |
| 장비 | 지역·정책별 빌드 | 출시 |
| 시설 레벨 | 지속 생산·지원 효율 | 출시 |
| 후원 정책 | 플레이어 개입의 행동 가중치 | 출시 |
| 신뢰·사가 | 지원 보정·스토리 기록 | 출시 |
| Ascension | 리셋형 장기 성장 | 후속 |
| 유물·신격 보구 | 고급 빌드 | 후속 |
| Paradox Spiral | 엔드게임 | 후속 |

### 9.2 출시 재화 4종

| 재화 | 획득 | 소비 | 성격 |
|---|---|---|---|
| 신력 | 영웅 활약·사가·업적 | 신전·후원 운영 | 플레이어 개입 자원 |
| 금화 | 원정·의뢰·판매 | 치료·운영·제작 | 마을 운영 자원 |
| 재료 | 전투·원정·생산 | 장비·시설 | 제작 자원 |
| 균열석 | 보스·장기 업적 | 고급 해금·회춘 강화 | 장기 성장 자원 |

기존의 `dr`, `enhanceStones`, `crackStones`, `tokens`, `sponsorGold`, `light`는 이 4종으로 통합하거나 비노출 상태로 둔다. 출시 1차에서 새 재화를 추가하지 않는다.

### 9.3 경제 곡선

```text
시설 업그레이드 비용
= 초기 비용 × 1.35^(시설 레벨 - 1)

시설 처리량
= 초기 처리량 × (1 + 0.18 × (시설 레벨 - 1))
```

소비 비율 목표:

- 50~60%: 영웅 성장
- 20~30%: 시설 운영
- 10~20%: 선택형 위험·편의·장기 수집

### 9.4 시간 기준

| 구간 | 다음 의미 있는 소비까지의 시간 |
|---|---:|
| 0~30분 | 30초~3분 |
| 30분~3시간 | 3~15분 |
| 3시간 이후 | 15분~2시간 |
| 오프라인 복귀 | 즉시 보상 또는 선택 1개 |

출시 1차 강화는 100% 성공한다. 강화 실패·장비 파괴·복구 비용은 라이브 운영 이후 별도 실험으로 둔다.

## 10. 오프라인 진행

### 10.1 기본 규칙

- 최대 8시간까지 누적한다.
- 오프라인 효율은 온라인 시뮬레이션의 70%다.
- 재접속 시 전체 전투를 재생하지 않고 결과 요약을 생성한다.
- 일반 전투·시설 작업·안전 원정은 자동 처리한다.
- 보스 도전·선택형 사건·회춘·영구 해금은 자동 확정하지 않는다.

### 10.2 오프라인 결과

```ts
interface OfflineSummary {
  processedSeconds: number;
  efficiency: number; // 0.7
  completedTaskIds: string[];
  completedExpedition: boolean;
  resourcesGained: Partial<Record<'spirit' | 'gold' | 'materials' | 'rift', number>>;
  equipmentGained: string[];
  wasClamped: boolean; // 8시간 상한 적용 여부
  clockAnomaly: 'backwards' | 'future' | 'invalid' | null;
  notes: string[];
}
```

결과 화면의 출시 선택은 단순하게 유지한다.

- 마을 확인: 정산된 작업·재화·장비를 확인하고 마을로 복귀한다.
- 재화 2배: 선택적으로 보상형 광고를 시청해 오프라인 재화만 2배 적용한다.
- 위험 Realm의 보스 결과와 다음 Realm 영구 해금은 결과 화면에서 별도 확인하기 전까지 보류한다.
- 미래 저장 시각·비유한 기기 시각·비유한 정산 효율은 보상을 확정하지 않고 사용자에게 상태를 알린다.

1. 영웅 이름·나이·현재 Realm
2. HP와 현재 행동
3. 현재 정책
4. 다음 완료 작업
5. 가장 가까운 의미 있는 목표

세부 수치·사가·로그는 2차 패널에 둔다.

### 11.3 온보딩

온보딩은 첫 15분 안에 다음 순서로 진행한다.

| 시간 | 경험 |
|---:|---|
| 0~1분 | 영웅 탄생, 신 역할 설명 |
| 1~3분 | 첫 전투와 첫 보상 |
| 3~6분 | 신전·회복당 작업 시작과 HP 회복 |
| 6~10분 | 대장장이와 첫 장비 교체 |
| 10~15분 | 원정소와 첫 원정 |
| 15~20분 | 첫 사건 선택, 지원 에이전트의 차이 설명 |
| 20~30분 | 첫 보스 준비, 회춘 개념 소개 |

## 12. 수익화·운영 정책

### 12.1 원칙

- 강제 전면 광고를 사용하지 않는다.
- 전투 승리를 직접 판매하지 않는다.
- 광고 제거는 구독이 아니라 영구 구매를 기본값으로 한다.
- 광고를 보지 않아도 핵심 콘텐츠를 완료할 수 있어야 한다.
- 결제 상품은 편의·추가 선택·장식 중심으로 구성한다.
- 모든 광고·IAP는 테스트 환경과 실제 플랫폼 환경에서 별도 검증한다.

### 12.2 출시 상품

| 상품 | 효과 | 비고 |
|---|---|---|
| 광고 제거 | 보상형 광고만 유지하고 비강제 광고를 제거 | 영구 구매 |
| 신력 보급 | 일정량의 신력 제공 | soft launch 데이터 확인 후 검토 |
| 재료 보급 | 기본 재료 제공 | soft launch 데이터 확인 후 검토 |
| 외형 꾸러미 | 영웅·마을 장식 | 후속 콘텐츠 |

균열석 판매와 보급 상품은 soft launch 데이터로 핵심 성장 압력을 확인한 뒤 재도입한다. 현재 V4 adapter의 출시 구매 표면은 광고 제거 하나이며, 광고·결제가 없어도 게임 진행은 계속된다.

### 12.3 보상형 광고

보상형 광고는 아래 중 하나로만 제공한다.

- 오프라인 결과 보상 2배
- 시설 작업 즉시 완료 1회
- 신의 개입 충전 1회
- (후속) 안전 원정의 추가 보상 선택

일일 최대 5회로 제한하고, 첫 20분 동안은 광고를 제안하지 않는다.

### 12.4 Live Ops

출시 직후에는 복잡한 시즌 패스 대신 다음 운영만 사용한다.

- 주간 신탁: 7일 동안 달성하는 단일 목표 3개
- 월간 사가: 영웅 기록을 기반으로 한 이야기 테마 1개
- 월 1회 밸런스 패치

시즌 패스와 다중 Realm 이벤트는 D1·D7·D30 데이터가 안정된 뒤 도입한다.

## 14. 기술 설계와 현재 코드 매핑

### 14.1 구현 위치 원칙

첫 출시 구현은 `games/inflation-rpg` 내부에 둔다. 두 번째 게임이 동일 의미로 재사용하기 전에는 `@forge/core`나 별도 genre core로 승격하지 않는다.

현재 구현 모듈은 다음과 같다.

```text
games/inflation-rpg/src/v4/
├── types.ts                 # V4 save·runtime contract
├── data.ts                  # 7시설·3에이전트·3Realm 정적 데이터
├── domain.ts                # 순수 작업·원정·정책·개입 계산
├── save.ts                  # schema 1·offline·V3 명시 import adapter
├── heroRuntime.ts           # V3 순수 전투/영웅 계산 경계
├── equipment.ts             # V4 장비 정의·레벨·능력치
├── monetization.ts          # AdMob/IAP optional adapter
├── useV4Game.ts             # V4 상태 commit·화면 callback
├── V4App.tsx
└── screens/
    ├── TownHubScreen.tsx
    ├── HeroDetailScreen.tsx
    ├── ExpeditionScreen.tsx
    ├── OfflineResultScreen.tsx
    ├── SagaScreen.tsx
    └── SettingsScreen.tsx
```

### 14.2 Store 책임

V4의 영속 상태 진원지는 `V4SaveEnvelope`이며 React `useV4Game`이 순수 domain 결과를 commit한다. 기존 `gameStore.ts`는 legacy V3 상태와 명시적 영웅 가져오기 adapter에만 사용한다.

스토어가 소유하는 상태:

- `V4SaveEnvelope.meta`의 영웅 외 영속 상태
- `V4SaveEnvelope.run`의 영웅·정책·원정 상태
- `lastProcessedAt` 기반 오프라인 처리 경계
- 광고 사용량과 광고 제거 entitlement는 V4 adapter/플랫폼 저장에 별도 보관

순수 시스템이 소유하는 계산:

- 전투 결과
- 오프라인 결과
- 시설 생산량
- 회춘 비용
- 원정 위험도
- 영웅 행동 선택
- 보상 분배

### 14.3 저장 migration

V4는 V3 persist version 27과 자동 migration 경계를 공유하지 않는다.

1. V4는 `schemaVersion: 1`과 `shin-ui-eternal-sponsor-v4-save-v1`을 사용한다.
2. V3 저장 키는 V4 로드·저장 과정에서 읽거나 덮어쓰지 않는다.
3. 영웅 상세의 “V3 영웅 가져오기”를 사용했을 때만 `migrateV3HeroSnapshot`이 실행된다.
4. adapter는 영웅 snapshot과 장비 기록만 V4 형식으로 복사하며 V3 재화·cycle·store mutation은 가져오지 않는다.
5. V4의 작업·시설·원정 링크는 로드 검증에서 대칭성을 확인한다.
6. 잘못된 시간·재화·정적 에이전트 정의·잠긴 Realm 상태는 V4 domain에 진입하기 전에 거부한다.

### 14.4 현재 검증 기준선 (2026-09-07)

- game Vitest: 398개 파일·3,449개 테스트 통과.
- V4 vertical slice: Chromium·iPhone14 30/30 통과(각 15/15).
- V3 legacy를 포함한 전체 game E2E: 44/44 통과(Chromium 22/22, iPhone14 22/22).
- monorepo typecheck·lint·circular 검사와 game production build 통과.
- 위 보호 파일 3종과 사용자 미추적 `output/`, `tmp/`는 V4 작업에서 수정·커밋하지 않는다.

## 16. QA·밸런스·출시 게이트

### 16.1 기능 QA

- 신규 저장에서 마을 → 첫 전투 → 첫 시설 → 첫 원정 → 첫 보스 흐름을 완료한다.
- 앱을 종료한 뒤 1시간·8시간 오프라인 결과를 각각 검증한다.
- 기기 시간 변경으로 보상을 무한 생성할 수 없어야 한다.
- 원정 중 앱 종료와 재실행에서 중복 보상이 없어야 한다.
- 회춘 직전·직후 레벨·장비·에이전트 신뢰도·사가가 보존되어야 한다.
- 작업 큐 취소·완료·앱 종료 상태가 일관되어야 한다.
- 저장 migration 이전 버전에서 새 상태가 안전하게 생성되어야 한다.

### 16.2 밸런스 QA

- 1,000회 신규 유저 시뮬레이션
- 100회 오프라인 8시간 시뮬레이션
- 100회 보스 도전 시뮬레이션
- 공격·비축·수련 정책별 진행 속도 비교
- 3개 Realm별 경제 유입·소비 비교
- 가장 효율이 낮은 시설이 30분 이상 방치되지 않는지 확인

### 16.3 모바일 QA

- iPhone 14 기준 390×844에서 주요 버튼 44px 이상
- Android 중간 성능 기기에서 30fps 이상 유지
- 백그라운드 복귀 후 Phaser 인스턴스 중복 생성 없음
- safe area·노치·가로 스크롤 없음
- 광고 표시 실패 시 게임 진행이 막히지 않음
- 구매 실패·취소·중복 callback을 안전하게 처리

### 16.4 출시 차단 조건

다음 중 하나라도 발생하면 출시하지 않는다.

- 오프라인 보상 중복 수령
- 저장 migration으로 기존 진행 손실
- 첫 15분 안에 다음 행동을 알 수 없는 상태
- 일반 콘텐츠에서 3회 연속 패배가 반복됨
- 광고 시청 실패로 보상이 영구 소실됨
- 결제 완료 후 상품이 중복 지급되거나 미지급됨
- 마을 시설을 강화해도 게임 플레이 변화가 보이지 않음

## 19. 최종 제품 판정 문장

출시 후보는 다음 문장을 만족해야 한다.

> 플레이어가 앱을 열었을 때 현재 영웅의 상태와 마을의 가장 큰 병목을 3초 안에 이해할 수 있고, 1~3분의 개입으로 다음 10분의 자동 진행을 바꿀 수 있으며, 다음 접속 때 확인할 가치가 있는 변화가 남아 있어야 한다.

이 문장을 만족하지 못하는 기능은 콘텐츠 수량이 많더라도 출시 우선순위를 얻지 못한다.
